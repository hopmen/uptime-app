# Ревью Uptime App

Результат — подтверждённые проблемы изменения, отсортированные от P0 к P4, с местом, последствиями и способом проверки исправления. Не исправляй замечания автоматически и не публикуй комментарии в GitHub по одному только запросу локального ревью.

## Получи точный состав изменения

Работай из корня репозитория. Прочитай корневой `AGENTS.md` и инструкции затронутых проектов. Используй локальные refs; если нужна актуальная удалённая база, выполни `git fetch origin` и явно зафиксируй её SHA. Для чтения diff не требуется checkout ревьюируемой ветки или изменение индекса.

```sh
git status --short --branch
git rev-parse HEAD
```

Выбери режим по запросу пользователя:

| Что ревьюим | Как получить diff и список файлов | Аргументы скрипта |
| --- | --- | --- |
| Ветка / PR относительно main | `git merge-base origin/main HEAD`, затем `git diff --no-ext-diff --no-renames <merge-base-SHA> HEAD`; список — те же аргументы с `--name-status` | `--base origin/main` |
| Один коммит | Получи SHA через `git rev-parse --verify <ref>^{commit}`; `git diff --no-ext-diff --no-renames <SHA>^ <SHA>` | `--commit <SHA>` |
| Индекс | `git diff --cached --no-ext-diff --no-renames`; список — с `--name-status` | `--staged` |
| Локальные изменения | `git diff --no-ext-diff --no-renames HEAD`; добавь содержимое новых файлов из `git ls-files --others --exclude-standard` | `--worktree` |

Для корневого коммита скрипт сравнивает с пустым Git-деревом; `git show --format= --root --no-ext-diff <SHA>` позволяет прочитать patch. Для merge-коммита по умолчанию сравнивай с первым родителем и явно сообщи это. `--base <ref> --head <ref>` сравнивает с merge-base, а не прямым diff двух вершин.

Если область не задана, при наличии локальных изменений используй `--worktree`, иначе ветку относительно `origin/main`. Не угадывай отсутствующий ref. Для PR проверь фактическую базу и head SHA, а не только номер PR. Полученный извне patch без доступного checkout допускает чтение, но проверки такого patch пометь как недоступные.

Прочитай весь diff, включая удаления, конфигурацию и зависимости. Большой diff читай частями по файлам; для сгенерированных OpenAPI/ReDoc проверь источник генерации и соответствие контракту, а не только HTML. При переименовании рассмотри оба пути. Изучи вызывающий код, реализации интерфейсов и тесты, чтобы проверить последствия; не превращай ревью изменения в аудит всех старых дефектов.

## Автоматические проверки до содержательного ревью

Сразу после определения области запусти скрипт с выбранным режимом, например:

```sh
python3 .codex/skills/project-code-review/scripts/run_checks.py --base origin/main --tests --build
```

Описание команд, ограничений и кодов выхода: [references/checks.md](references/checks.md). Скрипт сначала выполняет статические проверки, затем запрошенные тесты и сборку. Go и Next.js проверяются только при затрагивании соответствующей директории; проверки всего приложения обнаруживают нарушения в связанных пакетах. Для документации/навыков вне приложений остаётся проверка diff. Скрипт не устанавливает инструменты и зависимости и не исправляет файлы.

Убедись, что проверяется именно версия из diff. Для `--commit` и `--base` скрипт требует чистый checkout целевого SHA; для `--staged` — отсутствие незастейдженных и новых файлов. При несовпадении подготовь отдельный checkout с разрешёнными для задачи ресурсами или продолжи чтение diff, явно отметив, что проверки нужной версии не выполнены. Не очищай чужую работу. Перечитай `git status` после команд; сборка может обновить служебные файлы Next.js.

При ошибке инструментов/окружения сохрани ограничение и продолжи доступное ревью. Не повторяй сетевые или мутирующие действия без устранения причины. Сбой линтера сам по себе не определяет приоритет дефекта. Различай `passed`, `failed`, `blocked`, `skipped`, `not_applicable`; никогда не выдавай пропущенные проверки за успешные. Логи и JSON находятся в напечатанном временном каталоге; не включай из них секреты в ответ.

## Пройди чеклист

Прочитай [references/architecture.md](references/architecture.md), затем **каждый пункт** [references/review-checklist.md](references/review-checklist.md). Веди краткую матрицу: ID пункта → `проверено` / `проблема` / `не применимо` / `не проверено`, плюс свидетельство или причина. Общие пункты G применяй всегда; B, F, D и X — по условиям в чеклисте. Отсутствие соответствующего пути в diff не исключает секцию, если изменённый контракт влияет на другой слой. Не отмечай пункт проверенным только потому, что линтер прошёл.

При изменении HTTP API проверь Swagger-аннотации, DTO и сгенерированный контракт по `backend/AGENTS.md`; генерацию выполняй в изолированной копии, если она может изменить ревьюируемое дерево. При вопросах о Next.js 16.3.5 читай соответствующий раздел локальной документации `frontend/node_modules/next/dist/docs/`, как требует `frontend/AGENTS.md`. Не подменяй факты об установленной версии общими знаниями. Архитектурный reference — карта текущего проекта, а не запрет на обоснованное изменение архитектуры.

## Сформируй результат

Приоритет — срочность исправления по реальному ущербу, охвату и условиям воспроизведения. Чем меньше число, тем раньше исправлять и тестировать.

| Приоритет | Критерий |
| --- | --- |
| P0 — немедленно | Подтверждённая критическая компрометация (рабочий секрет, массовый обход авторизации), необратимая потеря данных или недоступность ключевого сервиса для всех. Блокирует выпуск. |
| P1 — высокий | Серьёзная уязвимость с конкретными условиями эксплуатации, нарушение изоляции пользователей, поломка входа/refresh/сохранения данных или другого основного сценария. Исправить до выпуска затронутой функции. |
| P2 — обычный | Воспроизводимая ошибка отдельных сценариев, нарушение контракта или архитектурная связность с показанным ущербом; существенный пробел тестов для нового поведения. |
| P3 — низкий | Локальное ухудшение поддержки, именования, доступности или лишний код с небольшими последствиями. Не повышай приоритет за один стиль. |
| P4 — рекомендация | Необязательное улучшение без доказанного дефекта. Выноси отдельно и только если полезно для запроса; не блокирует выпуск. |

Не называй любую проблему безопасности P0: укажи доступность атаки и последствия. Для пробела тестов объясни конкретный риск и недостающий сценарий, не придумывай процент покрытия. Не требуй исправления неизменённого старого кода, если изменение не создаёт и не усиливает проблему.

Сначала выдай замечания P0 → P3. Для каждого: `[P#] Краткое действие` → путь и узкий диапазон строк из изменённого кода → условие, наблюдаемое последствие и доказательство → минимальное направление исправления → тест/команда с ожидаемым результатом. Не публикуй значения найденных секретов. Не дублируй одну первопричину в нескольких замечаниях. Гипотезы с недостающим подтверждением укажи отдельно как вопросы, без выдуманного дефекта.

Затем кратко укажи область (режим, base/target SHA либо локальное состояние), результаты команд и ограничения, матрицу всех пунктов чеклиста (можно группировать ID с одинаковым статусом, сохраняя причины). P4 — отдельные рекомендации. Если дефектов нет, так и напиши; это не утверждение об отсутствии всех рисков. Предложи порядок исправления и проверки по возрастанию номера приоритета, когда замечаний несколько.
