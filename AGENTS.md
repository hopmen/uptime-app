# Правила репозитория

## Структура репозитория

В репозитории находятся два независимо запускаемых приложения:

- `backend/` — сервис на Go.
- `frontend/` — веб-приложение на Next.js.

Работайте только в проекте, к которому относится изменение. Не размещайте Go-код в `frontend/`, а веб-код — в `backend/`. Правила и команды для конкретного стека находятся в соответствующем `AGENTS.md` каждого проекта.

## Общие правила разработки

Группируйте предметные изменения по функциям и не включайте несвязанные рефакторинги в одну задачу. Не коммитьте сгенерированные зависимости, результаты сборки, локальные бинарные файлы и учётные данные. Храните секреты в неотслеживаемых `.env`-файлах; при добавлении новой настройки создавайте очищенный от секретов `.env.example`.

## GitHub Flow и ветки

- Перед началом каждой задачи создавайте отдельную ветку от актуальной `main`.
- Именуйте ветки в формате `feat/<nazvanie-zadachi>` для новой функциональности и прочих изменений или `fix/<nazvanie-zadachi>` для исправления ошибок.
- Название задачи пишите транслитом, строчными латинскими буквами; слова разделяйте дефисами. Примеры: `feat/istoriya-proverok`, `fix/oshibka-avtorizatsii`.
- Все изменения по задаче выполняйте в её ветке; не коммитьте напрямую в `main`.
- После завершения задачи и проверок создавайте Pull Request в `main`. Вливайте изменения только через PR, после прохождения обязательных проверок и ревью.
- Если пользователь просит оформить PR из текущей ветки, используйте её; отдельная ветка только для оформления этого PR не нужна.

## Коммиты

- Формат: Conventional Commits (feat, fix, refactor, test, docs, chore)
- Заголовок до 72 символов, в повелительном наклонении
- Без эмодзи, без «significantly improved» и прочей воды
- Тело — только если нужно объяснить «почему», а не «что»
- Один логический шаг — один коммит
- Пишите заголовки и тела коммитов на русском языке, сохраняя английский тип Conventional Commits.

## Pull Request

### Подготовка

1. Проверьте текущую ветку, `git status`, удалённый репозиторий и авторизацию GitHub CLI: `git remote -v`, `gh auth status`.
2. Обновите сведения об удалённой базе командой `git fetch origin`. Просмотрите все коммиты и итоговый diff текущей ветки относительно `origin/main`: `git log --oneline origin/main..HEAD` и `git diff origin/main...HEAD`. Описание должно отражать весь итоговый состав PR.
3. Выполните проверки по правилам изменённых проектов. Для backend — `go fmt ./...` и `go test ./...`; для frontend — `npm test`, `npm run lint` и `npm run build`. Если меняются миграции или сохранение данных, выполните доступный интеграционный тест с PostgreSQL. Для изменений только документации достаточно проверки diff. Если код не менялся после уже выполненных проверок, используйте их результаты, явно указывая, что они получены ранее.
4. Зафиксируйте только относящиеся к задаче изменения. Не включайте чужие или ранее подготовленные изменения пользователя без его указания; проверяйте индекс перед коммитом. Не добавляйте секреты, локальные `.env`, зависимости и результаты сборок.
5. Проверьте, нет ли уже открытого PR из текущей ветки в `main`. Если он существует, обновите его заголовок и описание; не создавайте дубликат.

### Заголовок и описание

- Оформляйте заголовок по Conventional Commits: `<type>[optional scope]: <описание>`, например `feat: добавь создание точек мониторинга сайтов`. Допустимые типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`.
- Пишите заголовок на русском языке, в повелительном наклонении, до 72 символов, без эмодзи и общих фраз. Тип выбирайте по основному результату PR, даже если в нём есть сопутствующие тесты или документация.
- Пишите описание на русском языке для ревьюера, который не видел переписку. Начинайте с решаемой задачи и поведения пользователя до и после изменения.
- Масштабируйте подробность по сложности. Для функциональных изменений используйте разделы: «Цель и результат», «Что изменено», «Проверки», «Как проверить вручную», «Миграции и ограничения».
- В «Что изменено» опишите затронутые части backend и frontend, новые API, хранение данных, валидацию, права доступа, тесты и документацию, если они менялись.
- В «Проверки» перечислите реально выполненные команды и их результаты. Отличайте локальные проверки от GitHub CI; явно отмечайте пропущенные проверки и причины. Не заявляйте об успешном CI или ревью без подтверждения.
- Дайте воспроизводимые шаги ручной проверки и ожидаемый результат. При наличии миграций укажите порядок применения, совместимость и откат; перечислите существенные ограничения реализации.
- При изменении состава PR обновляйте заголовок и описание по финальному diff, удаляя устаревшие сведения.

### Публикация и проверка

1. Отправьте текущую ветку командой `git push -u origin <ветка>` без force push.
2. Сохраните точное описание с настоящими переносами строк во временный UTF-8 файл вне репозитория. Создайте PR через `gh pr create --base main --head <ветка> --title '<заголовок>' --body-file <файл>`; для существующего PR используйте `gh pr edit`. Не передавайте многострочное описание через небезопасную подстановку shell.
3. Проверьте опубликованный PR: URL, заголовок, текст, исходную ветку, базу `main` и состав файлов через `gh pr view` и `gh pr diff --name-only`. Проверьте состояние CI через `gh pr checks`; отсутствие проверок не считайте успешным запуском CI.
4. Верните пользователю ссылку на PR и сообщите о незавершённых проверках или ограничениях. Не вливайте PR и не включайте автоматическое слияние без явного запроса пользователя.
5. Если remote, авторизация или права доступа отсутствуют, подготовьте доступные локальные изменения и описание, затем сообщите конкретную причину блокировки и какие данные нужны. Не утверждайте, что PR создан, пока GitHub не подтвердил создание.
