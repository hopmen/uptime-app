# Правила бэкенда

## Структура

Бэкенд является Go-модулем. Исполняемые точки входа размещайте в `cmd/` (сейчас это `cmd/server`), пакеты только для приложения — в `internal/`, а `pkg/` используйте лишь для пакетов, которые допустимо импортировать за пределами модуля. По мере разработки группируйте код мониторинга uptime по функциям.

## Команды

Запускайте эти команды из `backend/`:

```sh
go run ./cmd/server  # Запуск точки входа сервиса
go generate ./docs  # Генерация и валидация контракта OpenAPI из Swagger-аннотаций
go test ./...        # Запуск тестов всех пакетов
go fmt ./...         # Форматирование Go-кода перед коммитом
```

Не коммитьте скомпилированные бинарные файлы, результаты проверки покрытия и локальные `.env`-файлы.

## Стиль и тестирование

Следуйте идиоматичному Go. Имена пакетов должны быть короткими и в нижнем регистре; экспортируемые идентификаторы используйте в `PascalCase`, неэкспортируемые — в `camelCase`. Имена файлов должны быть описательными и в нижнем регистре, например `config.go` или `health_handler.go`.

Размещайте тесты рядом с исходным кодом, используя суффикс `*_test.go`. Для нескольких сценариев предпочитайте табличные тесты. После изменений запускайте `go test ./...`; добавляйте целевые тесты для нового поведения и исправлений ошибок.

## Swagger и OpenAPI

- Каждый новый HTTP-роут, включая публичные роуты, описывайте Swagger-аннотациями непосредственно над его обработчиком в `internal/server/`. При изменении или удалении роута обновляйте либо удаляйте соответствующие аннотации.
- Указывайте `@Summary`, уникальный `@ID`, `@Tags` и `@Router` с фактическими HTTP-методом и полным путём. Через `@Param` описывайте все входные параметры: path, query, заголовки, JSON-тело и multipart-поля. Указывайте тип, обязательность и назначение; для файлов используйте `formData file`.
- Описывайте форматы запросов и ответов через `@Accept` и `@Produce`, успешные ответы через `@Success`, ошибки через `@Failure`, значимые заголовки ответа через `@Header`. Коды статусов и схемы должны соответствовать обработчику; для ответов без тела не задавайте схему тела.
- Для защищённых роутов указывайте `@Security BearerAuth` или `@Security RefreshCookie` согласно фактической авторизации. Необязательную refresh-cookie описывайте параметром `Cookie` в заголовке: генератор преобразует его в cookie-параметр OpenAPI 3. Общие сведения и схемы авторизации поддерживайте в `cmd/server/main.go`.
- Используйте именованные DTO для тел запросов и ответов. В тегах полей поддерживайте JSON-имена, обязательность, ограничения, форматы и примеры в соответствии с реальной валидацией и сериализацией. При добавлении обработчиков или DTO в новые пакеты включайте их в области сканирования `cmd/openapi`, обновляйте проверки состава контракта в `internal/server/swagger_test.go`.
- После изменений роутов, параметров, DTO, ответов, кодов ошибок, авторизации, Swagger-аннотаций или генератора выполняйте из `backend/` команду `go generate ./docs`, затем `go fmt ./...` и `go test ./...`. Убедитесь, что генерация и валидация завершились успешно, и проверьте diff контракта на соответствие изменениям API.
- Коммитьте сгенерированные `docs/openapi.json` и `docs/openapi.yaml` вместе с исходниками, изменяющими контракт. Не редактируйте эти файлы вручную. Повторная генерация без изменений исходников не должна менять контракт. Подробнее о Swagger UI и генерации — в [README.md](README.md).
