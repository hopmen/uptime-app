# Создание и проверка миграций базы данных

Используй этот гайд, когда задача меняет схему PostgreSQL или требует преобразования существующих данных. Результат работы — новая миграция, согласованный с ней код приложения и проверенные сценарии применения и отката.

## Где находятся файлы и ресурсы

Все пути ниже указаны от корня репозитория.

| Путь | Назначение |
| --- | --- |
| [AGENTS.md](../../AGENTS.md), [backend/AGENTS.md](../../backend/AGENTS.md) | Правила репозитория, команды и требования к Go-коду |
| [backend/migrations/](../../backend/migrations/) | SQL-миграции: пара `<номер>_<название>.up.sql` и `<номер>_<название>.down.sql` |
| [backend/compose.yaml](../../backend/compose.yaml) | Локальный PostgreSQL и сервис `migrate` на базе `golang-migrate` |
| `backend/.env` | Локальные настройки и секреты; файл не коммитится |
| [backend/.env.example](../../backend/.env.example) | Пример настроек без секретов, включая подключение к БД |
| [backend/internal/store/](../../backend/internal/store/) | GORM-модели и запросы к PostgreSQL |
| `backend/internal/<пакет>/*_test.go` | Тесты рядом с изменённым кодом |
| [backend/internal/server/monitors_postgres_test.go](../../backend/internal/server/monitors_postgres_test.go) | Существующий интеграционный тест `TestMonitorPostgres`, использующий `TEST_DATABASE_URL` |

Схема управляется SQL-файлами. Запуск `backend/cmd/server` сам по себе не применяет миграции. Не подменяй миграции вызовами GORM `AutoMigrate`.

## Последовательность действий

### 1. Определи изменение и исходное состояние

Прочитай правила проекта и последние миграции. Найди затронутые таблицы, модели, запросы и тесты. Зафиксируй ожидаемую схему и поведение приложения после изменения.

Определи, какие данные уже могут находиться в таблицах: `NULL`, пустые значения, дубликаты, внешние ключи. Для новых ограничений подготовь преобразование существующих записей. Например, перед добавлением `NOT NULL` заполни отсутствующие значения, а перед `UNIQUE` разбери дубликаты.

Продумай порядок развёртывания миграции и приложения. При необходимости сначала добавь совместимую структуру, затем перенеси данные и переключи код; удаление старых полей вынеси в следующую миграцию. Оцени блокировки и объём обновляемых данных.

### 2. Создай новую пару SQL-файлов

Выбери следующий свободный номер по содержимому `backend/migrations/`. Сохраняй шестизначную последовательную нумерацию и название в `snake_case`. Например, если последняя версия — `000004`, следующая пара может называться так:

```text
backend/migrations/000005_add_monitor_status.up.sql
backend/migrations/000005_add_monitor_status.down.sql
```

В `up` опиши изменение схемы и необходимые преобразования данных. В `down` опиши обратные действия в порядке, учитывающем зависимости: сначала зависимые объекты, затем основные. Не редактируй уже применённые миграции; исправления оформляй новой версией.

Если откат удаляет данные, явно опиши потери и способ восстановления из резервной копии. Если полноценный откат невозможен, укажи ограничение и план восстановления. Пустой `down` не считается проверенным откатом.

Если нужна атомарность нескольких SQL-операций, используй явную транзакцию и проверь совместимость всех команд с ней. Операции, которые нельзя выполнять в транзакции, требуют отдельного подхода; учитывай это и в тестах.

### 3. Согласуй код, настройки и тесты

Обнови затронутые модели и запросы в `backend/internal/store/`, а также код соответствующей функции. Если появилась настройка, добавь её пример без секретов в `backend/.env.example`.

Добавь целевые проверки нового поведения и ограничений БД. Для преобразования данных подготовь записи в старой схеме, примени миграцию и проверь результат. Тест, создающий записи только после миграции, не проверяет перенос существующих данных.

### 4. Примени миграции на локальной проверочной БД

Используй отдельную локальную БД, данные которой можно изменять и откатывать. Перед выполнением команд проверь адрес подключения и назначение БД. Не используй рабочую БД для проверки отката.

Команды ниже выполняются из `backend/` и рассчитаны на стандартные значения из `.env.example`. Нужны Docker с Compose и доступный порт `5432`. Если параметры отличаются, согласуй URL в командах с `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` из локального окружения. Внутри Compose адрес сервера — `postgres:5432`, с хоста — `localhost:5432`.

```sh
docker compose up -d --wait postgres
```

Для команд мигратора определи функцию в текущем shell. Она использует тот же образ и каталог миграций, что и сервис `migrate`, но позволяет передать нужное действие вместо стандартного `up`:

```sh
migrate_local() {
  docker compose --profile migrate run --rm migrate \
    -path=/migrations \
    -database='postgres://uptime:uptime@postgres:5432/uptime?sslmode=disable' \
    "$@"
}
```

Проверь два сценария на отдельных проверочных БД:

1. **Установка с нуля.** На пустой БД выполни `migrate_local up`: вся цепочка должна примениться без ошибок.
2. **Обновление существующей схемы.** На другой пустой БД выполни `migrate_local goto <предыдущая_версия>`, подставив номер без угловых скобок. Добавь характерные данные старого формата, затем выполни `migrate_local up` и проверь их преобразование и сохранность. Версия должна соответствовать состоянию до добавленных в задаче миграций.

На каждой БД после применения выполни:

```sh
migrate_local version
migrate_local up
```

Ожидается последняя версия без состояния `dirty`. Повторный `up` должен сообщить об отсутствии новых миграций (`no change`), сохранив схему и данные. Это проверка учёта применённых версий мигратором; SQL-файлы не обязаны допускать ручное повторное выполнение.

### 5. Проверь откат и повторное применение

После успешного `up` и проверки данных выполни на проверочной БД:

```sh
migrate_local down 1
migrate_local version
```

Проверь возврат к предыдущей схеме и оговорённую сохранность данных. Затем снова выполни `migrate_local up` и проверь итоговую схему и поведение приложения. Если задача добавляет несколько версий, проверь откат всей добавленной последовательности и её повторное применение.

При ошибке проверь состояние БД и причину сбоя. Не используй `force` как способ исправить SQL: эта команда меняет учёт версии, но не выполняет миграцию. Восстановление после ошибки должно учитывать фактически выполненные операции.

## Как проверить результат

### Схема и данные

Подключись к проверочной БД:

```sh
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Через `\d имя_таблицы` проверь поля, типы, значения по умолчанию, индексы и ограничения. SQL-запросами проверь сохранность старых записей, результат преобразований и работу новых ограничений. Для каждой миграции заранее сформулируй конкретные ожидаемые значения; успешного завершения команды недостаточно.

### Код и интеграция

При изменениях Go-кода выполни из `backend/`:

```sh
go fmt ./...
go test ./...
```

Для существующего интеграционного теста укажи URL проверочной БД, доступной с хоста:

```sh
TEST_DATABASE_URL='postgres://uptime:uptime@localhost:5432/uptime?sslmode=disable' \
  go test ./internal/server -run '^TestMonitorPostgres$' -count=1 -v
```

Убедись, что тест завершился с `PASS`, а не `SKIP`. Без `TEST_DATABASE_URL` он пропускается. Тест создаёт отдельную схему внутри транзакции, выполняет все `*.up.sql` и в конце откатывает транзакцию; пользователь БД должен иметь право создавать схемы.

Этот тест проверяет создание и хранение точек мониторинга, а его проверка `down` относится только к миграции `000004`. Он не проверяет `schema_migrations`, состояние `dirty`, перенос старых данных или откат каждой новой миграции. Эти сценарии проверяй отдельно по шагам выше и целевыми тестами. Для SQL, несовместимого с транзакцией, подготовь отдельный сценарий проверки на одноразовой БД, поскольку текущий тест выполняет всю цепочку в транзакции.

Запусти приложение с обновлённой схемой и проверь затронутый пользовательский сценарий: создание, чтение и изменение соответствующих данных. Убедись, что в логах нет ошибок отсутствующих таблиц, колонок или несовместимых типов. Настройки из `.env` нужно передать в окружение процесса: текущий Go-сервер не загружает этот файл автоматически.

### Критерии готовности

- Новые версии уникальны, для каждой есть осмысленные `up` и `down`; ранее применённые файлы сохранены.
- Установка с нуля и обновление схемы с существующими данными проверены.
- Версия мигратора корректна, `dirty` отсутствует, повторный `up` не меняет БД.
- Откат и повторное применение проверены; ограничения восстановления данных описаны.
- Схема, модели, запросы и поведение приложения согласованы; целевые тесты прошли.
- Перед коммитом выполнен `git diff --check`, проверен состав изменений и отсутствие секретов.
- В PR указаны порядок развёртывания, ожидаемый результат, порядок отката, выполненные проверки и все пропущенные проверки с причинами. Если PostgreSQL или Docker недоступны, интеграционная проверка остаётся невыполненной.

При изменении только этого гайда достаточно проверить diff, команды по конфигурации проекта и локальные ссылки; выполнять описанные миграции не требуется.

Справка по аргументам: [golang-migrate CLI](https://github.com/golang-migrate/migrate/tree/v4.18.3/cmd/migrate).
